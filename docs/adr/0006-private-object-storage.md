# ADR-006: Use private object storage with signed access

**Status:** Accepted

**Date:** 2026-09-16

**Decision owners:** Stagenum maintainers

## Context

Stagenum will manage photos, videos, documents, invoice PDFs, receipts, and
exports associated with projects and financial activity. These objects may
contain addresses, worksite details, client communications, signatures,
financial information, or other private data.

Binary objects can be large and have different storage, delivery, retention,
and integrity requirements from relational business records. Routing every
upload and download through the application server would consume application
bandwidth and memory, while public object URLs would make revocation and
project-scoped authorization difficult.

Object storage cannot decide whether a person is currently entitled to view a
project. PostgreSQL remains authoritative for identity, project grants, object
metadata, business relationships, lifecycle state, and retention obligations.
The storage system provides durable bytes and scoped transfer capabilities.

## Decision

Stagenum will store evidence and generated binary documents in **private
object storage**. No object or bucket will be publicly readable or writable.

Authenticated application endpoints will authorize each operation using
PostgreSQL records and issue a short-lived, operation-specific signed URL or
equivalent scoped transfer grant. Clients may transfer bytes directly with the
storage provider, but possession of an object key alone never grants access.

The initial abstraction will target common object-storage semantics without
making a particular cloud vendor part of the domain model. A provider-specific
implementation may be selected during deployment.

## Decision details

### Objects covered

Private object storage will hold:

- provider-submitted project evidence;
- client-accessible evidence previews or derivatives;
- agreement and invoice documents;
- payment receipts;
- CSV and PDF exports;
- temporary files required for validated processing; and
- other generated binary artifacts whose metadata belongs in PostgreSQL.

Small structured business records, permissions, lifecycle states, audit events,
and financial ledger entries remain in PostgreSQL rather than being encoded as
object files.

### Metadata and authority

Every durable object has a PostgreSQL metadata record containing, as
applicable:

- an application-generated object identifier;
- the owning module and related project, stage, revision, invoice, or export;
- the storage provider, bucket or namespace, and opaque storage key;
- the object purpose and visibility classification;
- declared and detected media type;
- byte size and integrity digest;
- upload, validation, availability, quarantine, deletion, and retention state;
- original display filename after sanitization;
- creator and relevant actor attribution;
- creation, expiration, retention, and deletion timestamps; and
- version or replacement relationships.

Authorization is evaluated from current application records. A signed URL does
not become the authoritative permission record, and storage listings are never
used as the project database.

### Object keys and filenames

Storage keys are generated by Stagenum and are not derived directly from user
filenames, email addresses, project names, or other sensitive values. Keys use
unguessable identifiers and may include non-sensitive environment or object-
class prefixes for operations.

The original filename is display metadata only. It is normalized, length
limited, stripped of path behavior, and escaped when presented. File extensions
do not establish the actual media type.

Storage keys and bucket names must not be exposed as stable public URLs. They
also must not be treated as secrets; authorization remains mandatory even if a
key is disclosed.

### Upload authorization

The upload flow is:

1. An authenticated actor requests an upload for a specific authorized project
   context and declares expected name, media type, and size.
2. The application validates permission, allowed object purpose, file policy,
   quota, and current workflow state.
3. In PostgreSQL, the application creates a pending upload record with an
   expected size, allowed type, generated key, and expiration.
4. The application issues a short-lived signed upload grant restricted to that
   key, operation, size, and content requirements supported by the provider.
5. The client uploads directly to the private storage service.
6. The client or provider signals completion; a worker independently verifies
   the stored object and metadata.
7. The object remains unavailable until required validation succeeds and its
   metadata state becomes available.

An upload grant cannot list a bucket, read an existing object, overwrite an
unrelated object, select an arbitrary key, or remain reusable indefinitely.

Where the storage provider cannot enforce an expected property in the signed
grant, Stagenum verifies it after upload and rejects or quarantines violations.

### Download authorization

An authenticated download endpoint loads the current object metadata and
verifies:

- the requesting actor and active session or client grant;
- project and role scope;
- the object's visibility and lifecycle state;
- whether the object is available rather than pending, quarantined, expired, or
  deleted; and
- any document-specific restriction.

If authorized, the endpoint returns a short-lived signed download URL or
streams through an approved delivery layer when stronger controls are needed.
The signed grant is limited to one object and read operation.

Signed URLs are bearer credentials. They must use TLS, have the shortest
practical lifetime, remain out of logs and analytics, and not be stored in
durable client data. Expiration limits future use but cannot revoke a URL that
has already been used to copy the bytes.

### Passwordless client access

Passwordless client access does not produce a broadly reusable project storage
credential. The client first establishes an application session tied to a
specific invitation and project grant. Each object request is then authorized
through that session before a narrow signed URL is issued.

Revoking the project grant prevents issuance of new URLs. Previously issued
URLs remain usable only until their short expiration, which must be considered
when choosing the lifetime for sensitive evidence.

### Validation and quarantine

User-supplied uploads are untrusted. Before availability, Stagenum verifies as
appropriate:

- actual size against the approved limit;
- detected media type and permitted format;
- integrity digest and upload completeness;
- filename and metadata safety;
- malware or unsafe-content scan result;
- archive expansion, document, and image-processing limits; and
- whether the object still belongs to a valid pending upload.

Pending and quarantined objects are inaccessible to ordinary clients. File
parsers, preview generators, and scanners run with limited privileges and
bounded CPU, memory, time, and output size. Derived previews receive their own
metadata records and authorization rules.

Active-content formats may be rejected or delivered as attachments rather than
rendered inline. Content disposition, type, security headers, and separate
download origins will be configured to reduce script execution and content
sniffing risks.

### Immutable evidence and replacement

An evidence object attached to a submitted revision is not overwritten in
place. Corrections create a new object and, where necessary, a new submission
revision. Metadata records preserve the relationship between superseded and
replacement objects.

Generated invoices and receipts similarly use versioned or immutable keys.
Cache behavior and signed access must not cause one revision to display bytes
from another.

### Integrity and completion

Stagenum records a cryptographic content digest when practical and verifies it
at a trusted boundary. Provider entity tags are not universally treated as
content hashes because multipart upload and encryption can change their
meaning.

A storage upload does not become durable business evidence merely because an
object exists at a key. Completion requires a matching pending record,
successful validation, and an atomic PostgreSQL transition attaching the object
to the intended business record.

Unattached and expired uploads are removed by idempotent background cleanup.

### Encryption and provider configuration

Storage uses encryption in transit and provider-supported encryption at rest.
Production buckets or namespaces have:

- public access disabled at the account and bucket level where available;
- least-privilege application and worker identities;
- access logging and security monitoring;
- versioning or recovery controls where justified by retention requirements;
- lifecycle policies aligned with application retention states; and
- separate environments and credentials.

Customer-managed encryption keys may be introduced when regulatory, customer,
or incident-containment requirements justify their operational cost. Encryption
does not replace authorization, retention, or access auditing.

### Retention, deletion, and legal holds

PostgreSQL records the application's retention and deletion state. Storage
lifecycle rules act as a defense-in-depth cleanup mechanism, not the sole
source of retention policy.

Deletion is an explicit workflow that accounts for active projects, financial
records, disputes, legal holds, security investigations, backups, object
versions, and derived files. A removed object is not represented as deleted
until the operation is confirmed or its pending state is visible.

Object-lock or write-once capabilities may be used only for a defined retention
requirement because they can prevent legitimate deletion and increase privacy
and operational risk.

### Delivery and caching

Private objects are not placed behind a publicly cacheable URL. If a content
delivery network is added, it uses private origins and signed delivery with
cache keys and headers that cannot leak one actor's authorization to another.

Sensitive responses default to restrictive caching. Generated exports may have
shorter retention and access lifetimes than their underlying records.

### Failure handling

Database changes and storage operations cannot share one transaction. Stagenum
uses the transactional outbox and idempotent workers to reconcile:

- pending uploads that never arrive;
- uploaded objects whose completion callback is lost;
- validation failures and quarantined content;
- database records whose storage operation must be retried;
- deletion requests awaiting provider confirmation; and
- provider objects without a valid metadata record.

Periodic reconciliation compares authoritative metadata with provider state
without making bucket listings part of a user-facing request.

## Consequences

### Positive

- Evidence and generated documents remain private by default.
- Direct client transfers avoid routing large files through the application
  process.
- Current project authorization controls every newly issued access grant.
- Short-lived, single-object URLs limit the usefulness of leaked credentials.
- PostgreSQL preserves searchable ownership, lifecycle, audit, and retention
  metadata while object storage handles durable bytes.
- Immutable keys protect revision-specific evidence and financial documents.
- Provider-neutral boundaries preserve deployment options.

### Negative and tradeoffs

- Upload and deletion workflows become asynchronous and require reconciliation.
- A signed URL is temporarily usable by anyone who possesses it.
- Malware scanning, format validation, preview generation, and quarantine add
  worker and operational complexity.
- Database metadata and storage objects can become temporarily inconsistent and
  require observable recovery paths.
- Direct uploads require careful cross-origin, size, type, and key restrictions.
- Object versions, replicas, backups, and caches complicate complete deletion.
- Provider-neutral design cannot hide every difference in signing, checksums,
  lifecycle behavior, and consistency.

## Alternatives considered

### Store binary objects in PostgreSQL

PostgreSQL can store binary data and would provide atomicity with metadata, but
large evidence and documents would increase database size, backup cost,
replication load, and application transfer overhead. Relational metadata and
object-storage bytes provide a better operational boundary.

### Public objects with unguessable URLs

An unguessable URL is still a durable bearer credential. It cannot enforce
current project access, short expiration, revocation, or role-specific
visibility. Stagenum requires private storage and authorized access grants.

### Proxy every upload and download through the API

The API could centralize transfer control, but large media would consume
application bandwidth and memory and complicate scaling. Proxying remains an
option for exceptional files or stronger delivery controls, not the default.

### Store signed URLs in PostgreSQL

Signed URLs expire and embed temporary authority. Persisting them as object
identity would create stale credentials and increase exposure. Stagenum stores
stable provider/key references and signs each authorized operation when needed.

### Select one storage vendor in this ADR

A specific provider must eventually be configured, but the domain needs common
private-object and signed-transfer behavior rather than vendor-specific types.
Vendor selection belongs to deployment evaluation unless it changes these
security or lifecycle guarantees.

## Security and privacy implications

- Buckets, objects, and origins are private by default with public access
  prevention enabled.
- Signed URLs are short-lived bearer credentials and are redacted from logs,
  analytics, traces, referrers, and support tooling.
- Authorization uses current application state before every signing operation.
- Object keys reveal no user identity, project name, filename, or authorization
  secret.
- Uploads are untrusted until validated and released from quarantine.
- Workers, scanners, and generators run with least privilege and cannot access
  unrelated object classes without need.
- Storage access, administrative actions, retention overrides, and manual
  downloads are auditable.
- Cross-environment access is prohibited, and production objects are never used
  as development fixtures without approved de-identification.
- Incident response includes the ability to stop signing, revoke application
  sessions, rotate storage credentials, quarantine objects, and investigate
  access logs.

## Validation and enforcement

The implementation will enforce this decision through:

- infrastructure checks that fail when public bucket or object access is
  enabled;
- integration tests for upload and download authorization across provider and
  passwordless client roles;
- tests confirming signed grants are restricted by operation, key, expiry, and
  supported size or content conditions;
- validation tests using mismatched types, oversized files, malformed content,
  unsafe filenames, and incomplete uploads;
- tests that quarantined, expired, deleted, and cross-project objects cannot be
  downloaded;
- reconciliation tests for missed callbacks, orphan objects, retries, and
  deletion failures;
- checks that immutable revision and financial documents cannot be overwritten;
- monitoring for signing failures, validation backlog, orphan counts, access
  denials, unusual download volume, and lifecycle-policy failures; and
- periodic recovery and deletion exercises that include versions and derived
  objects.

## Revisit triggers

A new ADR should reconsider this decision when:

- regulatory or customer requirements demand customer-managed keys, regional
  isolation, write-once retention, or stronger download controls;
- object volume, transfer cost, or geographic latency requires a CDN or
  multi-region strategy;
- media processing becomes a separately scaled subsystem;
- a storage provider cannot meet defined durability, deletion, signing, or
  audit requirements;
- offline mobile access requires a controlled encrypted-device storage model;
  or
- evidence authenticity requires additional capture attestation, trusted
  timestamps, or chain-of-custody controls.
